# AI 작업 절차

## 1. 시작 전

1. `git status --short --branch`로 기존 변경을 확인한다.
2. 사용자 변경과 현재 작업 범위를 분리한다. 관련 없는 파일을 되돌리거나 포맷하지 않는다.
3. 요청이 API·도메인 변경이면 Controller부터 Service, Repository, entity, 테스트, REST Docs까지 실제 호출 흐름을
   추적한다.
4. 외부 연동·스케줄러·보상·배치가 포함되면 `operations-and-security.md`를 읽고 실패·재시도 경계를 확인한다.

## 2. 구현

- 요청에 필요한 최소 파일만 바꾼다.
- 기존 도메인의 국소 관례를 지키되, 새 도메인에는 표준 계층을 적용한다.
- 엔드포인트 계약을 바꾸면 프런트가 사용하는 필드와 enum 값의 호환성을 점검한다.
- 데이터 삭제, 대량 수정, 배포 설정 변경은 명시적 요청 없이 하지 않는다.

## 3. 검증

1. 변경한 Service 또는 Controller의 관련 테스트를 실행한다.
2. API 문서를 바꿨다면 Docs 테스트와 `./gradlew build`를 실행한다.
3. `git diff --check`로 공백 오류를 확인한다.
4. 결과에는 실제 실행한 명령, 통과·실패, 실행하지 못한 항목과 이유를 구분해 적는다.

## 4. Git과 PR

- 기본 대상은 `main` 또는 `dev`이며, 실제 요청·현재 팀 흐름에 맞는 대상 브랜치를 확인한다.
- 커밋 전 `git diff`와 `git status`를 확인해 의도한 파일만 stage한다.
- 로컬 Docker, IDE, 환경 파일, 빌드 산출물은 기능 코드와 함께 자동으로 포함하지 않는다.
- 커밋 메시지는 `feat:`, `fix:`, `test:`, `docs:`, `refactor:` 중 의도를 나타내는 접두사를 사용한다.
- PR은 `.github/PULL_REQUEST_TEMPLATE.md` 형식을 채우고, 동작 변화와 검증 결과를 적는다.

사용자가 명시하지 않은 커밋·푸시·PR 생성은 하지 않는다.
